## Bajaj Finserv Health — Distributed Payment Settlement Bug (Production Debugging)

Debugged a complex intermittent production bug affecting ~0.3% of transactions where doctors were not receiving payouts even though patients were successfully charged.

### System Architecture
```
Patient Payment → Razorpay → Payment Service → Doctor Payment Service → Kafka → Payout Service → Salesforce → Settlement Ledger
```

### Investigation Approach
Used correlation IDs (paymentId, invoiceId, traceId, externalTransactionId) propagated across all services. Used Elasticsearch + Kibana to reconstruct full request lifecycles for affected transactions.

**Anomaly found:**
- Razorpay webhook received successfully
- Payment service acknowledged with HTTP 200
- PAYMENT_CAPTURED event existed in Kafka
- No corresponding payout creation log

Kafka consumer lag and message loss were ruled out — offsets were committed successfully.

**Root Cause:**
Kafka offset commit happened BEFORE the database transaction for payout creation completed. During Kubernetes pod autoscaling/rebalance:
1. Kafka message consumed
2. Offset committed
3. Database transaction begins
4. Pod rebalance/restart happens
5. Transaction rolls back
6. Kafka thinks message already processed → event permanently lost

Only triggered under high throughput + autoscaling — extremely difficult to reproduce.

**Confirmation:** Correlated pod restart timelines from Kubernetes events with Kafka rebalance timestamps and DB rollback logs. Reproduced in staging with artificial Salesforce latency injection.

### Fix (Multi-Layer)
1. **Kafka offset handling:** Offsets committed only after successful DB commit
2. **Idempotent payout creation:** Deterministic payout IDs + DB uniqueness constraints + safe replay
3. **Outbox pattern:** Events persisted atomically in outbox table, published asynchronously by relay worker — eliminated DB/Kafka state inconsistency
4. **Resiliency:** Graceful shutdown hooks, consumer drain logic before rebalance, circuit breakers, retry queues, alerting for payout-to-settlement SLA breaches

**Tools used:** Elasticsearch + Kibana, Prometheus + Grafana, Kubernetes event logs, Kafka consumer group metrics, MongoDB transaction logs

### Outcome
- Payout inconsistencies dropped to zero
- No events lost during deployments or autoscaling
- Reconciliation jobs stopped detecting captured-but-unsettled payments
- Deployment-related payout incidents eliminated

## Bajaj Finserv Health — DoctorsAuth: OAuth-Inspired Authentication Microservice

Designed and implemented a production-grade authentication and authorization microservice for the multi-tenant doctor platform.

### Context
Multi-tenant ecosystem where a single clinic could have multiple doctors, receptionists, assistants, and supplier-linked users accessing shared resources. Required balancing security, low-latency authentication, multi-device session management, instant revocation, and seamless UX.

### Token Architecture
**Dual-token model:**
- Access Token: 1-day expiry, separate signing key
- Refresh Token: 30-day expiry, separate signing key

**JWT payload (rich authorization claims):**
- doctorId, clinic/facilityId
- Role and permissions
- Supplier mappings
- Subscription plans
- Platform metadata
- Feature-level entitlements

Downstream microservices (appointments, EMR, prescriptions, billing) authorized requests locally without calling the auth service on every request.

### Multi-Tenant Access
A receptionist could operate on behalf of multiple doctors under the same clinic; a doctor could belong to multiple facilities. Solved using a `mappingId` abstraction embedded into the token as the tenant/session boundary.

### Hybrid Stateless-Stateful Architecture
- JWTs for fast stateless verification
- MongoDB-backed session tracking for revocation and concurrent session control
- Every login created an `ActiveUser` session record (refresh token, access token hash, platform, mappingId, last activity, device metadata)

### Token Refresh Flow
1. Client sends refresh token
2. Signature validated
3. Session existence verified in MongoDB
4. Account state checked (active/suspended/force logout)
5. Subscription and role mappings revalidated
6. New access token generated
7. Session metadata asynchronously updated

Permissions and subscription plans revalidated on every refresh — enabling immediate enforcement of downgrades, clinic access removals, and deactivations.

### Force Logout Semantics
`forceLoggedoutAt` timestamp updated on: password change, MFA enabled, permissions update, suspicious activity, account suspension.

During refresh: if `forceLoggedoutAt > token.iat`, refresh rejected and user forced to reauthenticate. Near-instant global session invalidation without maintaining a JWT blacklist.

### Concurrent Device Management
Configurable max concurrent session limits with automatic FIFO eviction of oldest sessions. Doctors could be logged in from clinic desktop, phone, receptionist terminals, and tablets simultaneously.

### Production Edge Cases Handled
- **Token replay attacks:** Refresh tokens validated against DB to prevent reuse after logout
- **Tampered tokens:** Separate access/refresh signing secrets
- **Stale authorization:** Permissions refreshed dynamically on token refresh
- **Token expiration races:** Clock-skew tolerance added
- **Cross-platform isolation:** Web and mobile sessions isolated via platform metadata
- **Refresh storms:** Distributed locking + token refresh deduplication for simultaneous mobile refresh requests
- **Revoked account access:** Suspension immediately blocked future refreshes

### Performance
- JWT validation: ~2ms average
- Refresh requests: sub-50ms P95
- Supported tens of thousands of concurrent active sessions

### Observability
- Structured audit logs for all auth flows
- Refresh failure tracking
- Suspicious refresh pattern alerts
- Correlation IDs across auth and downstream services
- Prometheus metrics: refresh latency, token issuance rate, failed validation attempts

## Bajaj Finserv Health — CI/CD Pipeline Optimization (Systemic Fix)

### Problem Identified
Pipelines across multiple teams (Doctor Listing API, DRx UI Automation, multiple microservices) were taking 15–30+ minutes per run, compounding across dozens of daily deployments. The pain was systemic, not isolated.

### Root Causes Found (via instrumentation + stage-level timing analysis)
1. No dependency caching — packages re-downloaded from scratch every run (consuming 30–50% of build time)
2. Sequential test/build execution despite independent stages
3. Bloated Docker images including dev dependencies
4. Suboptimal build tooling (Maven/npm where Gradle/Yarn were better fits)
5. Artifacts rebuilt multiple times across stages instead of reused

### Fixes Implemented
1. **Dependency caching** — Azure Pipeline Cache with lock-file-based cache keys (yarn.lock, package-lock.json, pom.xml). Yarn zero-install for frontend. Gradle build cache + incremental compilation for Java.
2. **Parallel job execution** — Restructured pipelines to run independent stages concurrently. Applied to DRx UI Automation and others.
3. **Docker optimization** — Multi-stage Dockerfiles (builder + runtime), reordered instructions for layer cache reuse, .dockerignore cleanup, dev dependency removal from runtime images.
4. **Build tooling migration** — Migrated Doctor Listing API from Maven to Gradle.
5. **Artifact reuse** — Standardized Azure Pipeline Artifacts (Publish/Download) to pass build outputs between stages, eliminating redundant builds.

Published findings as an internal reference guide and on Medium — adopted as org-wide CI/CD standards.

### Measurable Results
- >70% reduction in build time via dependency caching (Doctor Listing pipeline)
- 40–50% reduction in total runtime via parallelization (DRx UI Automation)
- 30–40% reduction in build time from Gradle migration (Doctor Listing API)
- Docker image sizes reduced >50% for several services
- Overall average pipeline execution time reduced by >50%
- Practices became org-wide standards, multiplying benefit across all adopting teams
